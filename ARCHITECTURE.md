# Основа масштабирования BoyGame

Приложение остаётся статической PWA без обязательного сервера и сборки для запуска.
Каталог, интерфейс, правила настольных игр, хранение и загрузка модулей разделены.

## Каталог и добавление игры

1. Добавьте запись в `js/game-catalog.js`: устойчивый `id`, файл, возрастные группы,
   значок, ключи перевода, сложности и ограничения доступа. Порядок записей задаёт
   порядок карточек. ID используется в сохранённом прогрессе: его нельзя менять
   при переименовании игры в интерфейсе.
2. Создайте `js/games/<id>.js` и зарегистрируйте реализацию:

   ```js
   App.register('my-game', function (root, App) {
     // root — контейнер игры; App.gameLevels('my-game') — сложности для возраста.
     // Для заданий используйте UI.uniqueGenerator(..., 'my-game').
     return function cleanup() { /* снять таймеры и обработчики */ };
   });
   ```

3. Добавьте переводы названия и описания в оба словаря `js/i18n.js`.
4. Выполните `node tools/sync-assets.cjs`. Команда обновит список `ASSETS` в `sw.js`
   и общий идентификатор сборки в `js/release.js`. Отсутствующие файлы, игры вне каталога
   и повторные ID считаются ошибкой. Дополнительные изображения и звуки игры
   перечисляйте в поле `assets` записи каталога: они также попадут в офлайн-кэш.
   Зависимости правил перечисляйте в `scripts` (файлы из `js/engines/`).
5. Выполните `node --test tests/*.test.cjs` и `node tools/sync-assets.cjs --check`.
   Перед выпуском поднимите номер кэша `boygame-vNN` согласно `AGENTS.md`.

Node.js нужен только для инструментов разработки (Node 18+). Опубликованное
приложение продолжает запускаться с обычного статического сервера.

## Доступ и жизненный цикл

- Метаданные берутся из каталога; регистрация привязывает к ним `start(root, App)`.
  Прежняя форма `App.register({ id, start })` поддерживается, но метаданные из неё
  не заменяют каталог. Все игры должны присутствовать в каталоге.
- `App.startGame(id)` проверяет возраст, ранг и дневной лимит до запуска игры.
  Возвращает Promise с результатом запуска. Во время подготовки истории и загрузки
  кода показывается состояние загрузки; уход в меню отменяет ожидающий запуск.
  `App.gameAccess(id, mode)` возвращает решение, а `App.requireGameAccess(id, mode)`
  также показывает объяснение ограничения. Проверяйте режим в момент нажатия.
- Для шахмат и шашек каталог содержит отдельные режимы: обучение открыто сразу,
  партии требуют ранга «Гений». Локальный `?test=1` даёт доступ без записи данных.
- Игра возвращает `cleanup()` либо `{ destroy, pause, resume }`. `destroy` обязателен,
  `pause` и `resume` добавляются парой. Очистка вызывается не более одного раза.
- `App.pauseGame()` и `App.resumeGame()` возвращают `false`, если режим не поддержан.
  «Падающие фигуры» используют эти методы; время на паузе не расходует дневной лимит.
- Результат передаётся через прежний `App.finishGame(id, stars, replay, note, level,
  nextLevel)`. Поздний результат уже закрытой игры не начисляется. При повторе
  `replay` сбрасывает состояние раундов, при уходе из игры `destroy` снимает ресурсы.
- Сессия не регистрирует таймеры автоматически. Каждый модуль обязан останавливать
  собственные таймеры, анимационные кадры и обработчики в `destroy`/`cleanup`.

## Проверки и данные

`tests/baseline.test.cjs` закрепляет возрастные наборы, сложности, получение нижних
кубков за прохождение сложного уровня, сохранение и изоляцию профилей, историю
заданий и отсутствие записи в демо. `tests/foundation.test.cjs` проверяет каталог,
переводы, доступ, жизненный цикл и обработчики офлайн-кэша. Тесты используют
отдельные JS-контексты и хранилище в памяти, пользовательский браузер не открывают.

## Модули и CSS

`js/app.js` управляет каталогом, загрузкой и запуском. `js/app/` содержит разделы
профилей, главного экрана, родителей, согласий, админки, наград и диалогов.
`js/engines/` содержит правила шахмат и шашек без обращения к DOM.

Стили подключены в прежнем порядке: `styles.css`, `games/learning.css`, `app-ui.css`,
`games/arcade.css`, `games/board.css`, `animations.css`, `theme.css`.
`theme.css` содержит завершающие переопределения; порядок ссылок в HTML значим.

## Хранение и миграции

- Профили, звёзды, рекорды, рейтинг, настройки и согласия сохраняют прежние ключи
  и формат localStorage. Общая версия схемы — `boygame.schemaVersion = 1`.
- `Store.ready()` подготавливает хранилище до запуска интерфейса. История профиля
  хранится в IndexedDB `boygame-history`, версия 1: `tasks` с ключом
  `[profile, game, signature]`, индексом `profile` и таблицей `migrations`.
- Импорт прежней истории и отметка версии проходят в одной транзакции. Прежний
  `taskHistory` в localStorage остаётся резервной копией. При повторном открытии
  импорт объединением подбирает также записи старой версии и локального fallback.
- `Store.prepareHistory()` вызывается перед запуском игры для активного профиля.
  Игровой API `Store.taskHistory` / `Store.rememberTask` остаётся синхронным;
  записи в IndexedDB начинаются сразу и отслеживаются через `Store.flush()`.
- При недоступности IndexedDB используется прежнее хранилище. При ошибке записи
  IndexedDB накопленная история сохраняется туда целиком. Ошибка сохранения
  localStorage показывается пользователю. Новая неизвестная версия схемы не
  перезаписывается старым приложением.
- Демо пропускает запись схемы и работу с IndexedDB. История не обрезается.
  Явный сброс/удаление профиля очищает также его историю IndexedDB; незавершённые
  удаления помечаются в `historyResets` и повторяются при следующем запуске.
- Время игры накапливается в памяти, сохраняется каждые 10 секунд, при переходах,
  смене профиля, уходе в фон и `pagehide`. Учитывается последний отрезок до паузы;
  время скрытой страницы и приостановленной игры исключено. При аварийном завершении
  процесса браузера без событий последние несохранённые секунды могут быть потеряны.
- `UI.uniqueGenerator` принимает необязательный пятый аргумент — функцию полного
  набора кандидатов. Тогда исчерпание доказано перебором. Для случайных генераторов
  лимит попыток означает предложение повторить подбор, а не завершение коллекции.
  Вызов генератора с предикатом `next(prefer)` предпочитает указанный тип;
  отклонённые кандидаты не записываются в историю. Если подходящий тип не найден,
  используется другой свежий вариант.

## Загрузка и выпуск

Главный экран использует метаданные без выполнения игровых модулей. `GameLoader`
подключает зависимости и игру по необходимости, объединяет одновременные запросы
и допускает повтор после ошибки загрузки. Статическая PWA сохраняет в кэше все игры.

Идентификатор сборки вычисляется из содержимого ресурсов и Service Worker.
Версионированные запросы модулей обслуживаются из соответствующей сборки. Service
Worker отдаёт оболочку и ресурсы из активного кэша до принятия обновления, сохраняет
предыдущий кэш для вкладок во время перехода и не кэширует API или чужие ресурсы.

После любых правок фронтенда выполните генератор, затем `--check` и тесты. Перед
выпуском повысьте `CACHE` согласно `AGENTS.md` и ещё раз выполните генератор.
Ручное редактирование `js/release.js` или массива `ASSETS` будет обнаружено проверкой.

`tests/storage.test.cjs`, `rules.test.cjs`, `loader.test.cjs` покрывают хранение,
таймер, правила и загрузку. `tests/browser-storage.html` проверяет настоящий
IndexedDB на временных тестовых базах; она не обращается к пользовательской базе
и localStorage. Для проверки полного офлайна используйте отдельный тестовый origin:
откройте демо, дождитесь установки PWA, остановите только его локальный сервер,
перезагрузите страницу и откройте игры. Это не меняет сетевые настройки компьютера.

Каждая итерация начинается со снимка. Публикация выполняется только по явной команде.

`tests/playthrough.test.cjs` проверяет полные сессии, запись наград, повторный
запуск и завершение настольных партий на синтетическом DOM с виртуальными часами.
`tools/release-check-server.py` позволяет проверить реальный переход PWA со старого
Git-коммита и замерить загрузку в браузере; хранилище подменяется до исполнения
кода приложения. Результаты и пределы этих проверок описаны в
[отчёте](reports/2026-10-25-release-checks.md).
