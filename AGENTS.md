# Инструкции для агента — BoyGame

## 1. ОБЩИЕ ПРИНЦИПЫ

- **Главный источник правил** — файл `AGENTS.md` в корне проекта. Всегда руководствуйся им.
- **Не угадывай разрешение.** Если есть хоть малейшее сомнение — НЕ ДЕЛАЙ, а задай уточняющий вопрос пользователю.
- **Никогда не действуй вслепую.** Явное разрешение пользователя обязательное там, где это указано.
- **Соблюдай структуру проекта.** Любые изменения должны быть согласованы с существующими стилем, неймингом, архитектурой и паттернами кода.

## 1.1 СНИМОК ПЕРЕД ИЗМЕНЕНИЯМИ

- Перед первой правкой в каждой отдельной задаче создай локальную точку восстановления проекта.
- Если рабочее дерево чистое, создай локальную ветку-снимок от текущего `HEAD` с именем `codex/snapshot-<краткое-имя-задачи>-YYYY-MM-DD`. Не переключайся на неё и не отправляй её на сервер.
- Если в рабочем дереве уже есть изменения, сначала зафиксируй весь снимок через `git stash push --all -m "snapshot before <краткое имя задачи>"`, затем сразу восстанови рабочее состояние командой `git stash apply --index stash@{0}`. Проверь, что исходные staged, unstaged, untracked и ignored файлы вернулись; сохрани stash как точку отката и не удаляй его автоматически.
- Если снимок или восстановление состояния завершились с ошибкой, не редактируй проект, пока исходное состояние не восстановлено.
- В конце сообщай пользователю идентификатор снимка (имя ветки, commit SHA или stash), чтобы его можно было найти для отката. Не выполняй разрушительный откат без прямой просьбы пользователя.

## 2. ДЕПЛОЙ — ТОЛЬКО ПО ЯВНОЙ КОМАНДЕ

**Категорически запрещено БЕЗ прямой команды пользователя:**
- `git push`, `git push origin *`, `git push --force`, `git push --force-with-lease`
- Создание тегов релизов (`git tag`, `git push --tags`)
- Любые действия, которые приводят к автоматической публикации на GitHub Pages
- Изменение настроек GitHub Pages, CNAME или деплой-конфигураций

**Разрешено БЕЗ подтверждения:**
- Чтение, анализ, редактирование файлов
- `git add`, `git add -A`
- `git commit` (только с осмысленным сообщением на русском или английском)
- Запуск локального сервера для проверки
- Проверка в браузере (строго с соблюдением раздела 3 «Безопасность данных»)

**Порядок публикации (выполнять ТОЛЬКО после явной команды: «пушь», «деплой», «опубликуй», «задеплой», «выложи»):**
1. Проверить текущее состояние: `git status`, `git diff --staged`
2. **Поднять версию кэша** в `sw.js`: изменить `boygame-vNN` → `boygame-v(NN+1)` (обязательно)
3. **Проверить `ASSETS` в `sw.js`** — добавить/удалить файлы из списка, если они были добавлены/удалены в проекте (HTML, CSS, JS, иконки, шрифты)
4. Закоммитить изменения: `git add -A && git commit -m "Краткое описание изменений"`
5. Выполнить пуш: `git push origin main`
6. **Дождаться 1–2 минуты** пока GitHub Pages пересоберёт сайт
7. Проверить работоспособность на живом URL: `https://games.veidon.ru/` (или `https://veidon1986.github.io/boy-game/`)

## 3. БЕЗОПАСНОСТЬ ДАННЫХ — КРИТИЧЕСКИ ВАЖНО

Проект хранит **все данные ТОЛЬКО локально** в `localStorage` браузера. Их **НИКОГДА** нельзя удалять или перезаписывать при тестировании.

**Ключи localStorage, которые НЕЛЬЗЯ трогать:**
- `boygame.profiles` — список всех профилей детей
- `boygame.activeId` — ID активного ребёнка
- `boygame.d.<id>.*` — все данные конкретного ребёнка (прогресс, статистика, звёзды, лучшие результаты, достижения, дневные лимиты, использование времени)
- Все остальные ключи, начинающиеся с `boygame.` (`boygame.sound`, `boygame.lang`, `boygame.adminUntil`, `boygame.theme` и др.)

**КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО при тестах (особенно на живом сайте `games.veidon.ru`):**
- Вызов `localStorage.clear()` (полная очистка хранилища)
- `localStorage.removeItem()` для любых ключей `boygame.*`
- Перезапись, обнуление или модификация ключей `boygame.*`
- Очистка хранилища через DevTools → Application → Clear Storage в отношении данных приложения
- Сброс пользовательских данных без **явного письменного разрешения пользователя**

**ПРАВИЛО ПРОВЕРКИ:**
- **Никогда не модифицируй** пользовательские данные в той вкладке браузера, где они уже есть.
- Для тестирования с чистым состоянием используй **Приватное/Инкогнито-окно**, **отдельный профиль браузера** или **локальный сервер** (`python3 -m http.server 8765`).
- При проверке на живом сайте — только **наблюдение, чтение и проверка UI/логики**, без любых манипуляций с `localStorage`.

## 4. ПРОВЕРКА В БРАУЗЕРЕ

- **Предпочтение — локальная проверка.** Перед любыми изменениями, влияющими на UI/логику, проверяй локально (`http://localhost:8765`).
- **Живой сайт (`games.veidon.ru`) — только для финальной верификации.** Не используй его для экспериментов, не чисти и не меняй в нём данные.
- **Не делай массовых «быстрых проверок»**, которые могут случайно затронуть хранилище.
- **При работе с админ-панелью** — НИКОГДА не трогай `localStorage`. Достаточно просто ввести пароль `boygame-admin` в существующей вкладке (там, где данные уже есть).

## 5. SERVICE WORKER (PWA)

- Проект — чистый HTML/CSS/JS, PWA с `sw.js`.
- **Обязательно** поднимай версию кэша `CACHE` в `sw.js` при любых изменениях фронтенда (HTML/CSS/JS/изображения), которые должны попасть на прод.
- При локальной разработке, если видишь проблемы с кэшем — либо подними версию, либо сбрось Service Worker в DevTools (только в **локальном** окружении, не трогая данные пользователя).
- Массив `ASSETS` в `sw.js` должен всегда соответствовать фактическому набору файлов в репозитории.

## 6. РАБОТА С GIT

- Рабочая ветка — `main`. Она подключена к GitHub Pages.
- Делай осмысленные коммиты. Описывай **что именно** изменил, а не «правки».
- Предпочитай атомарные коммиты (одно логическое изменение — один коммит).
- Перед коммитом всегда проверяй `git diff` — что именно попадёт в изменения.
- **Никогда не делай `git push` без явной команды пользователя** (это жёстко закреплено в `opencode.jsonc` и в этом документе).

## 7. КОД И КАЧЕСТВО РАБОТЫ

- **Сохраняй обратную совместимость.** Не ломай существующую логику без веской причины и без обсуждения.
- **Уважай существующий код.** Изучай окружающий код перед изменениями. Не переписывай без необходимости.
- **Не удаляй и не перезаписывай пользовательскую работу.** Относись к любым незнакомым файлам/изменениям как к потенциальной работе пользователя — сначала исследуй, потом действуй.
- **Используй правильные инструменты.** Предпочитай `edit` для точечных правок, `write` — только для создания новых файлов или полной замены (не для мелких изменений).
- **Параллелизируй независимые вызовы инструментов** там, где это уместно.
- **Чистота вывода.** Не пиши в ответе шум (лишние разделители, дубли). Отвечай чётко и по делу.

### Правило неповторяющихся заданий

- При генерации раундов любой игры исключай задания, уже показанные этому профилю: используй `UI.uniqueGenerator` с ключом игры и устойчивой подписью содержания задания; для специальных генераторов сохраняй подпись через `Store.rememberTask`.
- История относится к профилю ребёнка и не сбрасывается при обычном запуске или смене игры. Демо-режим не записывает её.
- Для конечных наборов расширяй коллекцию или варианты задания. Если набор исчерпан, явно сообщай об этом; не выдавай знакомый вопрос незаметно как новый.
- Фиксированные правила и стартовая позиция настольной партии не считаются заданиями. Упражнения с конкретным правильным ответом должны получать новую задачу или вариант, если игрок уже видел эту задачу.

## 8. ИНСТРУМЕНТЫ OpenCode

- Правила работы с инструментами заданы в окружении. **Не выдумывай** несуществующие инструменты, эндпоинты или возможности.
- Вызывай только те инструменты, что явно предоставлены.
- При работе с `edit` — обязательно сохраняй точные отступы (пробелы/табы), не добавляй префиксы строк.
- `oldString` в `edit` должен однозначно находиться (добавь больше контекста, если есть множественные совпадения, либо используй `replaceAll` только когда это действительно нужно для всех вхождений).

## 9. ЗАПРЕТЫ (ЧЁТКИЙ СПИСОК)

- **НИКОГДА** не чистить `localStorage` на живом/рабочем сайте.
- **НИКОГДА** не пушить в `main` без явной команды пользователя.
- **НИКОГДА** не удалять пользовательские данные (профили, прогресс, достижения).
- **НИКОГДА** не тестировать потенциально деструктивные действия на живых данных.
- **НИКОГДА** не изменять правила деплоя в обход этого документа.

## 10. ФИНАЛЬНАЯ ПРОВЕРКА ПЕРЕД КОММИТОМ

Перед тем как сделать коммит (особенно если планируется деплой — но только по команде):
- [ ] Изменения соответствуют задаче
- [ ] Нет случайных правок (лишние пробелы, отладочный код)
- [ ] Service Worker обновлён, если затронут фронтенд
- [ ] Изменения не затрагивают пользовательские данные
- [ ] Код консистентен с окружающим
- [ ] Результат проверен локально
